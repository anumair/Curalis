Queue:pg-bossSlot Hold Mechanism
We will implement the slot hold mechanism entirely within PostgreSQL by treating a hold as a temporary appointment record rather than relying on an external cache such as Redis. When a patient selects a time slot, the system creates an appointment with the status HELD and a hold_expires_at timestamp set to 10 minutes in the future. During availability checks, only active holds (status = HELD and hold_expires_at > NOW()) and confirmed appointments are considered unavailable, allowing expired holds to be ignored immediately even if they have not yet been cleaned up. When the patient confirms the booking, the appointment status is updated from HELD to CONFIRMED within the same database transaction. If the patient does not complete the booking within the allotted time, a background pg-boss worker periodically marks expired holds as EXPIRED, keeping the database clean. This approach maintains PostgreSQL as the single source of truth, ensures transactional consistency, eliminates synchronization issues between multiple data stores, and provides a simple, reliable, and production-ready solution for temporary slot reservations.

Doctor leave conflictsWe'll implement doctor leave as a controlled workflow rather than a simple database update. When an administrator requests leave for a doctor, the system will first identify and preview all affected appointments, allowing the administrator to review the impact before confirming the action. Upon confirmation, the leave record is created, affected appointments are updated to CANCELLED_BY_CLINIC (instead of being deleted), and background jobs are queued to send notification emails, remove Google Calendar events, and provide patients with a one-click rescheduling link. The booking transaction will also verify doctor leave within the same database transaction (protected by an advisory lock on the doctor) to prevent race conditions where a patient books an appointment while leave is being applied. The system will support both full-day and partial-day leave, ensuring only overlapping appointments are affected.
Notification Reliability-outbox pattern

We'll implement notification delivery using the Outbox Pattern. Whenever an appointment is booked, cancelled, or rescheduled, the system will store both the business data (e.g., appointment) and a corresponding notification request in a notification_outbox table within the same PostgreSQL transaction. A background pg-boss worker will continuously process pending notifications, send emails through the email provider, and update their status upon success. Failed deliveries will be retried using exponential backoff, with a maximum retry limit before being moved to a failed notifications state for administrator review. Each notification will include an idempotency key to prevent duplicate emails during retries or network timeouts. For scheduled reminders, workers will always verify the latest appointment status before sending a notification, ensuring cancelled or rescheduled appointments do not trigger unnecessary reminders. This design guarantees reliable, fault-tolerant notification delivery without impacting the responsiveness or consistency of the booking process.
Google Calendar
We'll implement per-user Google OAuth 2.0 for both patients and doctors, allowing each user to securely connect their own Google Calendar. During the OAuth flow, encrypted refresh tokens will be stored in PostgreSQL, while short-lived access tokens will be generated automatically whenever calendar operations are required. Appointment creation, rescheduling, and cancellation will trigger asynchronous background jobs that create, update, or delete events in both the patient's and doctor's calendars, with the corresponding Google Event IDs stored alongside the appointment for future synchronization. The system will automatically refresh expired access tokens, retry failed calendar operations, and ensure no clinical information is exposed in calendar events or email subject lines, preserving patient privacy while delivering a seamless scheduling experience.

LLM Integration
The platform will integrate the LLM asynchronously using pg-boss, ensuring that AI processing never delays the appointment booking process. Once a patient successfully books an appointment, the system immediately stores the appointment details along with an AI summary record having the status PENDING, and a background worker is queued to generate the pre-visit summary. The LLM will be instructed to return a structured JSON response containing the urgency level, chief complaint, and suggested questions for the doctor. The response will be validated using Zod before being stored in the database. If the validation fails, the system will automatically retry the request once; if it still fails, the summary status will be marked as FAILED, allowing the doctor to continue reviewing the patient's original symptom form without interruption. The prompts will explicitly instruct the LLM not to provide medical diagnoses or treatment recommendations, ensuring that the generated summaries serve only as a pre-consultation aid for clinicians and not as a replacement for professional medical judgment. The same asynchronous workflow will be used after the consultation, where the doctor's clinical notes and prescription are processed by the LLM to generate a patient-friendly post-visit summary, which is then stored and made available to the patient.

Timezones 
We will store all appointment timestamps in UTC (timestamptz) while storing each doctor's IANA timezone (e.g., Asia/Kolkata) separately. Working hours will be interpreted in the doctor's local timezone and converted to UTC when appointments are created or queried. This approach ensures accurate scheduling across different regions and prevents issues caused by daylight saving time or server timezone differences.

To prevent concurrent double-booking, PostgreSQL enforces an exclusion constraint that disallows overlapping appointments for the same doctor while the appointment status is `HELD` or `CONFIRMED`. Since expired `HELD` records cannot be excluded dynamically using `NOW()` inside the constraint, the booking service handles constraint violations by checking whether the conflicting record is an expired hold. If so, it atomically marks that hold as `EXPIRED` and retries the insertion once. If the conflicting appointment is still active or already confirmed, the request is rejected with HTTP 409 (Slot No Longer Available). A background pg-boss worker additionally cleans up expired holds periodically to keep the database free of stale reservation records.


Doctor writes the prescription through a structured form containing Medicine Name, Dose, Frequency, Duration, and Instructions. The prescription is stored in normalized database tables rather than free text, allowing the system to automatically generate medication reminders without relying on AI. When the prescription is saved, the backend materializes all reminder instances into a `medication_reminder` table using predefined mappings for common frequency codes (e.g., OD, BD, TDS, QID, HS). Each reminder is assigned a UTC `scheduled_at` timestamp based on the patient's timezone. A pg-boss background worker periodically checks for pending reminders whose scheduled time has arrived, sends the reminder email, and marks it as completed. Reminder generation stops automatically when the medication course ends, a new prescription replaces the existing one, or the patient chooses to disable medication reminders.
